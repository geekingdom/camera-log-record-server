# CameraLogRecordServer 工程开发规范

本文件完整保留用户要求制作成Skill的十六类规范，仅含开发规范；具体业务合同由工程现行代码、模型和专项文档维护。

## 一、适用范围与要求继承

1. 本规范适用于 CameraLogRecordServer 工程后续所有开发、维护、问题排查、重构、测试、文档及交付对话；进入新的对话仍须继承。

2. 开始工作前，必须识别本轮目标、用户最新更正、交付范围、验收条件及尚未完成的既有要求，不能只处理最后一条消息而遗忘前面仍有效的任务。

3. 用户后续明确更正的要求，替代同一事项的旧要求。历史建议、早期方案、旧摘要和旧文档不能覆盖用户后续确认的决定。

4. 区分长期规范、具体业务要求和一次性授权。某次允许删除旧数据、忽略特定失败或暂停推进，不得自动转化为未来工作的永久规则。

5. 不得将助手提出但未经用户接受的建议，写成用户已经确认的强制要求。

6. 对已经存在的工程约定，应先检查其实际适用范围与当前实现。发现规则、文档和代码不一致时，明确指出并核实，不能自行选择最方便的一种作为依据。

## 二、上下文压缩与跨对话恢复

1. 每次自动上下文压缩或基于摘要恢复后，必须在实质性工作前读取并执行：

   `/Users/geekingdommac/.codex/skills/post-compaction-continuity/SKILL.md`

2. 恢复时必须核对以下内容：原始目标、用户更正、约束、验收标准、已完成事项、未完成事项、当前工程与分支、已有验证证据，以及准备执行的下一步。

3. 恢复顺序以最新业务消息、工程当前状态总表、Git 工作区状态、最新提交、相关源码和验证产物为依据。摘要仅用于定位线索。

4. 摘要中的推测、未确认事实和可能过时的状态必须重新验证。不得把推测直接继承为已确认结论。

5. 从第一个未完成步骤继续，保留已经完成的工作及仍然有效的验证结果，不得因为上下文压缩而重新开始、重复开发、缩小范围或降低验收标准。

6. 生成摘要、汇报状态、用户询问进度，不得被误判为替代原业务目标的新任务。

7. 持续工作期间维护简短的连续性记录，包含目标、修正、已完成、待完成、验证证据、阻塞项和下一步，不依赖收到压缩通知后才临时补写。

8. 如果关键历史无法恢复，应明确说明缺失内容及影响，不能编造先前要求，也不能声称已经完成无法验证的前后比较。

## 三、需求推进与进度管理

1. 工程当前状态统一以以下文件作为进度入口：

   `docs/implementation-status.md（相对工程根目录）`

2. 状态总表逐项记录最终要求、实现位置、验证证据、未完成部分及下一步，内容必须与当前代码和提交状态一致。

3. 每次实质性的源码、配置或测试变更，都要同步更新对应需求的状态和证据。

4. 历史实验、逐轮排查过程和过往验收记录放入独立历史文档；当前总表保留清晰的现行状态，避免累积大量过时的“进行中”“待验证”描述。

5. 对多项需求，应先梳理依赖关系、实施顺序和验收点，避免只持续优化局部问题而遗漏工程整体交付。

6. 问题修复应检查同类代码和相关调用链。用户要求全工程排查时，不能仅修复最先暴露的一处错误后结束。

7. 用户明确要求暂停时，按照当次指定范围完成收尾后停止；用户恢复任务后从未完成部分继续。普通状态询问不构成暂停指令。

## 四、CodeGraph 使用规范

1. 工程开发必须使用 CodeGraph 辅助理解代码、定位符号及评估变更影响。

2. 修改前先在工程根目录执行：

   ```sh
   codegraph sync .
   ```

3. 对本轮涉及的关键符号执行影响分析：

   ```sh
   codegraph impact <符号>
   ```

4. 根据影响结果检查相关调用方、被调用方、接口、状态处理及测试，不能只修改目标文件而忽略关联路径。

5. CodeGraph 是辅助分析工具，结论必须通过实际源码、测试或运行证据确认。

6. CodeGraph 不可用或分析失败时，应说明原因及实际采用的替代检查，不能声称已经完成未执行的图谱分析。

## 五、Subagent 使用与主代理职责

1. 对能够拆成独立任务的功能实现和多步骤工程工作，应使用 subagent；无依赖的任务优先并行执行。

2. 派工前明确每个子任务的目标、范围、输入、交付物和验收条件，划分文件或模块责任，避免交叉修改。

3. 沿用现有用户级规则：每个 subagent 使用 **`gpt-5.6-terra`，推理强度 `medium`**。

4. 在运行环境允许的并发额度内安排独立任务；有空余容量和可独立开展的工作时继续派工，达到额度后复用空闲或已完成的 subagent。

5. 不把某次会话的固定槽位数量写成工程永久并发上限，实际并发以运行环境为准。

6. 主代理负责总体设计、任务拆分、依赖协调、子代理衔接、代码审核、冲突处理、集成验证、进度维护及最终交付。

7. 子代理报告“完成”不等于工程任务已经完成。主代理必须检查实际产物、验证证据和集成结果。

8. 子代理应使用工程已有环境和约定，不能因没有定位到解释器或工具路径而直接认定工程缺少测试依赖。

9. 指定模型不可用或并发受限时，必须如实说明，不能擅自更换模型后声称遵守了指定要求，也不能虚构已运行的子代理。

## 六、技术框架与模块组织

1. 延续工程已有技术框架：Python/FastAPI 后端、Vue3/TypeScript 前端、MongoDB 数据存储，以及当前已经采用的配套工具链。不得在普通需求中擅自替换主要框架。

2. 前后端必须分层、分类和模块化，公共能力、业务功能与应用装配职责清晰分离。

3. 后端公共模块归入现有 `common` 层，各业务职责归入对应功能模块；前端共享能力归入 `shared`，功能界面归入 `features`，装配入口归入 `app`。

4. 优先复用已有模块、公共组件、校验逻辑和工具，避免建立重复实现或平行维护的同类机制。

5. 单文件保持合理规模，**建议不超过 500 行**。确有必要保留较大文件时，应有清晰职责；不能通过压缩成一行或机械拆分规避模块化要求。

6. 修改模块时检查职责边界和依赖关系，避免把接口、业务、持久化、后台任务及界面逻辑混在同一处。

7. 重构和性能优化必须保持已确认的对外行为及数据语义；涉及行为变化时，明确说明并按需求变更处理。

## 七、中文说明与代码可维护性

1. 源码应有完整、清晰的中文模块说明。

2. 公共函数、关键状态转换、并发控制、异常处理及恢复逻辑，应使用中文说明其职责、约束和处理依据。

3. 注释重点解释为什么这样处理、依赖什么前提以及有哪些边界，避免只重复代码字面含义。

4. 部署、维护及验证脚本应有详细中文说明，明确可配置项、执行条件、操作影响及结果判断方式。

5. 代码保持清晰可读，避免为了减少行数而增加理解和维护成本。

## 八、异常处理、资源管理与故障调查

1. 所有关键流程必须考虑成功、失败、超时、取消及中断情况下的处理和收尾。

2. 连接、文件句柄、后台任务、子进程、订阅及临时资源必须有明确生命周期，防止泄漏、重复占用或长期残留。

3. 对结果不明的操作，应保留“不确定”状态及证据，不能简单当作失败后无条件重试。

4. 并发和恢复逻辑应明确所有权、版本、幂等及状态转换边界，防止旧回调、旧任务或迟到请求影响当前状态。

5. 局部异常应合理隔离，避免单个任务或后台流程的阻塞扩散为整个服务不可用。

6. 故障分析以原始日志、源码、复现及实际运行证据为依据，建立时间和事件之间的对应关系。

7. 明确区分已确认事实、合理推测和待验证事项；缺少证据时不得断言唯一根因。

8. 不得用提高阈值、隐藏告警、吞掉异常或移除验证来代替问题修复。

## 九、运行日志与审计规范

1. 服务运行、用户操作及相关异常必须有足够的记录，支持定位发生时间、操作对象、操作者、来源、执行结果及失败原因。

2. 请求与异常应能通过请求编号或关联标识追踪；异常日志保留有用的调用栈和上下文。

3. 日志应结构清晰、含义明确，避免大量“未记录”、模糊摘要或无法关联对象的信息。

4. 对未变化状态及无效重复日志合理降噪，同时保留首次异常、状态变化、持续异常所需摘要及恢复记录。

5. API、后台执行组件及关联模块的日志应能够共同排查问题，不能只检查单侧日志就下结论。

6. 日志输出必须脱敏，不记录密码、令牌、认证头、私钥等秘密；排障所需信息应以安全且有界的方式记录。

7. 运行日志应具备轮转和保留机制，避免无限增长，也避免因固定少量分片而丢失故障调查所需历史。

## 十、接口模型与 API 文档维护

1. 接口定义、服务端校验、实际响应和文档必须一致，修改接口时同步检查全部关联内容。

2. 请求字段及 Query、Path 参数的中文说明应声明在实际接口模型或参数定义中。

3. JSON 响应使用运行时校验的响应模型；新接口优先直接声明 `response_model`。

4. 字段说明必须准确解释实际业务含义、单位、枚举、空值和时间边界，不能只根据字段名称套用通用描述。

5. HTTP 文档从实际 OpenAPI 模型生成，WebSocket 文档依据实际发送帧模型生成，避免独立维护一套容易失真的字段释义。

6. 不得只维护示例而缺少完整合同；缺少字段说明或真实响应不匹配时，应由测试发现并失败。

7. 接口名称应清楚表达用途，避免重名、歧义和难以理解的描述。

8. 每个对外接口提供可复制、可适当修改使用的 Python 示例，并保持参数、权限、返回内容及错误处理与当前接口一致。

9. 内部协调字段和敏感字段不得因模型或投影疏漏而泄露到公开响应中。

## 十一、数据库设计与变更规范

1. 新增集合、持续写入流程或显著改变写入频率时，同时评估增长速率、记录规模、保留期、恢复引用、幂等引用和查询索引。

2. 数据保留与清理必须考虑活动任务、恢复流程和关联引用，不能仅根据终态就直接设置 TTL。

3. 索引设计覆盖实际默认列表和高频筛选，避免脱离真实查询建立索引。

4. 使用真实 MongoDB Explain 验证索引、扫描量及排序，不能用 MongoMock 结果证明索引命中或事务原子性。

5. 索引升级检查既有名称、字段顺序和选项，支持重复初始化及多进程启动，不得无依据删除旧索引。

6. 涉及多个记录一致性、并发修改和操作重放时，依据实际需求使用事务、版本比较、CAS 与幂等机制，并验证竞争和回滚场景。

7. 数据迁移及清理应有范围、批次、重入和结果检查机制，避免启动时无界处理或不可恢复的批量修改。

## 十二、前端质量与部署配置规范

1. 前端保持企业级质量，与工程已有视觉风格一致；普通功能修改不得擅自整体替换风格。

2. 页面和组件适配桌面与移动端，合理处理长内容、滚动、缩放及不同分辨率，避免重叠、遮挡和关键操作不可达。

3. 异步请求及界面切换应处理取消、迟到响应、重复提交和旧状态覆盖等问题。

4. 布局或样式调整不得无意重建后台操作、重复订阅或改变业务状态。

5. 部署配置尽量集中，常用环境差异通过环境配置管理，避免要求用户修改多个源码文件才能部署。

6. 更新用户现有配置时，应以其当前完整配置为基础，保留已有有效项，明确新增、删除和变更内容。

7. 工程应保持现有部署方式之间的配置与功能一致性；部署相关变更必须检查受影响的各部署路径。

8. 内网依赖源、离线条件及公开 CI 环境差异，应通过明确配置处理，避免只适配开发机或某一台服务器。

9. 环境配置、部署脚本、文档及 Skill 均不得写入真实凭据。

## 十三、测试与验证规范

1. 使用工程已有虚拟环境、依赖及脚本；执行前确认解释器和工具位置，避免因 PATH 问题误判工具缺失。

2. 根据变更范围执行有意义的专项测试，并完成工程要求的基线检查：

   ```sh
   pytest -q
   ruff check backend tests scripts
   ```

   前端执行：

   ```sh
   npm test
   npm run build
   ```

3. 影响布局、实时显示或下载交互时，执行相关真实浏览器验证；按工程约定运行 `scripts/browser_smoke.mjs`，检查桌面和移动端截图。

4. 浏览器验证应关注交互、异步状态、实际布局和控制台异常，不能仅以页面打开或构建成功代替验收。

5. 数据库事务、并发、索引及真实协议相关修改，应使用能够证明对应行为的集成验证，不能只依赖替身测试。

6. 性能相关修改应有可重复的测量，说明数据规模、环境、持续时间、指标口径及前后结果，同时验证正确性未被破坏。

7. 严格区分模拟测试、本机短时测试、真实协议测试、实机验证及公司环境持续验收，结论不得超出证据范围。

8. 测试失败时应定位原因、修复并重新验证；不得通过跳过、删除关键断言或放宽合同来制造通过结果。

9. 验证结果必须对应最终代码；后续修改影响原有证据时，补跑相关检查，不能继续引用已失效的结果。

## 十四、测试数据与临时环境清理

1. 开发实验结束后及时清理本轮自建的模拟数据、临时下载副本、测试数据库及专属进程，避免长期占用资源。

2. 清理前确认来源、路径归属、任务收尾状态、活动作业和引用关系，不能仅凭名称判断是否可删除。

3. 不得清空全局日志目录、缩短全局保留期或删除真实设备日志来完成测试清理。

4. 使用清理工具时优先预览；只对有充分归属证据且符合工具范围的产物执行实际删除。

5. 保留简短实验报告、结果摘要和必要证据。失败实验需保留时，记录原因及下一步处理方式，不得无限积压。

6. 一次性重建环境或删除旧数据的授权，只适用于当次明确范围。

## 十五、Git 提交流程与格式

1. 工程代码统一使用指定仓库：

   ```text
   git@github.com:geekingdom/camera-log-record-server.git
   ```

2. 启用并遵守工程已有 Git 钩子及提交模板，通过 `scripts/install-git-hooks.sh` 安装或核验配置。

3. 每次提交使用**中文标题和详细中文正文**，正文必须包含：

   ```text
   背景：
   变更：
   测试：
   影响：
   ```

4. 各段填写有实际信息的中文说明，不得用空话、占位符或重复标题凑数；同时满足工程提交检查脚本的约束。

5. 提交前检查差异、测试结果、文档及状态记录，确保提交范围清楚，不混入凭据、原始日志、下载产物或无关变更。

6. 交付流程为：

   **完成实现与集成 → 完成验证 → 更新状态和文档 → 中文提交 → 推送 → 等待该提交完整 CI → 修复失败并重新验证 → 全部成功后交付。**

7. 自动提交和等待 CI 属于既有工程交付流程。用户本轮明确要求仅分析、仅审核或暂不提交时，按本轮范围执行，不扩大为代码变更与提交。

8. 不得以本机测试通过、推送成功、部分 CI 成功或旧提交 CI 成功，替代本次最终提交的完整 CI 结果。

9. 功能提交后又产生修复、文档或验收记录提交时，应核对最终交付提交对应的 CI，不能停留在前一提交的成功状态。

10. CI 失败后继续定位、修复、提交和等待，直至满足交付条件；外部阻塞无法解决时明确报告，不能宣称已经完成。

11. 历史某轮允许忽略特定制品上传失败的授权，不得推广为未来可以忽略 CI 失败。
