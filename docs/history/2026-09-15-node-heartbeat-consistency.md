# 跨机节点心跳判定一致性

## 已确认的代码缺陷

后台配置的 `_is_online` 只检查心跳距离当前小于30秒，没有排除未来时间；节点健康的 `fresh` 则拒绝未来超过2秒。这能复现同一节点一处在线、一处离线。旧健康信息把所有失败均描述成“超过30秒未收到节点心跳”，无法区分未来时间、格式无效和无心跳。

前端另用浏览器 `Date.now()` 与心跳、遥测对比。访问电脑时钟不正确时，即使API判定健康，页面也可能显示失联或隐藏遥测。时区名称不同不等于绝对时钟不同；UTC与北京时间正确换算不会产生此问题。

## 修复与边界

- 后台配置和健康共用同一30秒窗口，允许未来最多2秒；分别描述缺失、非法、过期及未来时间。
- `/api/v1/nodes` 每个节点附带UTC `assessedAt`，与其健康结论采用同一时刻。
- 列表接收响应时用 `performance.now()` 锚定服务器时间，Vue代理通过 `toRaw` 访问同一快照。页面驻留期间继续老化；浏览器墙上时钟变化不再影响在线或遥测显示。旧API无新字段时兼容旧逻辑，因此应同时更新API和前端。
- 不变更Worker心跳写入、调度/隔离/租约时钟，不凭登记状态绕过新鲜度。API与Worker实际时钟差异仍须通过可信时间源同步。

## 目标环境待核对

目前用户未提供目标节点响应和服务器时间，以上只证明代码缺陷及修复，不证明目标服务器确由时钟偏差造成。对比两API同一节点ID，并查看 `heartbeat`、`assessedAt`、`health` 和A/B的 `date -u`。未来心跳应优先检查时钟同步；持续旧心跳则检查Worker进程、数据库连接、节点ID及部署版本。
