# 保存节点配置的即时准入验证

## 问题与修复

用户要求后台保存节点容量即可生效。本轮双 Worker 验收准备发现，调度候选及领取事务仍可能按旧心跳中的 `accepting` 和 `capacity` 分配任务。最初四项回归全部失败：保存关闭准入后仍能领取、收紧容量后仍能领取、调度仍选择已关闭的 A、扩容后仍被旧心跳上限拒绝。

`tasks/scheduler.py` 以保存配置筛选候选并计算容量；`tasks/claim.py` 在既有配置写栅栏内重新检查准入和容量。并发保存导致事务冲突后重新读取，不建立孤立运行或连接锁。节点健康、心跳、隔离、磁盘和写入压力条件仍然必须满足；打开准入并不绕过节点健康检查，正在运行的任务不因容量收紧而被强行终止。

## 已验证

- `tests/test_scheduler_saved_admission.py` 六项通过，涵盖上述四项和调度批次扩容/缩容。相邻调度、竞争、速率准入共29项通过；随后单独增加的批次两项也通过。
- `scripts/verify_input_admission.py` 真实本机 MongoDB 副本集：在配置事务写栅栏前提交外部更新，速率收紧、关闭准入、容量缩小均拒绝；回读任务归属、运行和端点锁无部分写入。容量从1放宽至2，保留容量1的原心跳，已有一个占用仍可领取。随机数据库在 finally 删除。
- 后端全量1438项通过，另新增批次两项通过；前端156项与生产构建通过，无超过500 kB的产物告警。本轮没有修改前端源码。
- `scripts/benchmark_scheduler.py` 使用随机数据库、8个模拟节点和500个待分配任务。单次真实事务调度周期3966.983 ms，全部领取，单节点最多63个。随机数据库已删除。该数据不证明500路日志采集、文件可读P99或全天容量。
- 重载前主库活动任务、节点归属、活动日志作业和端点锁均为0。只重载API，PID从17073变为30882；Worker17074及前端保持运行，8000/8001/5173健康检查均200。此为本机时点证据，不代表后续实时状态或正式环境部署。

## 边界

管理员在本周期候选读取之后修改配置时，事务复核仍会阻止越过新准入条件，下一调度周期再选择节点。扩大容量不能替代CPU、磁盘、网络及持续吞吐验收；当前没有目标Linux服务器，物理隔离与全天容量仍待具备环境后验证。
