# 管理配置正式接口审计事务

基线为 `863ada8`，持续推进整体工程目标中的“每次操作与异常可追溯”，不把本模块完成视为整个 R26 已完成。

## 行为变化

平台保留期 PATCH、节点登记 POST、节点配置 PATCH、来源 IP 策略 PATCH 原先先修改配置再追加审计。现统一复用 `audited_mutation`：业务写入、版本检查和成功审计共享 Mongo session，以快照事务、majority+journal 提交。审计写入失败则不发布业务配置，也不会推进版本。

GET 的惰性默认值属于系统初始化；首次直接 PATCH 时，默认记录保障和用户更新都在同一事务中，失败不留下默认记录。节点登记不会伪造 `nodes` 心跳；节点重名仍为 409，旧版本仍为 409，未登记更新仍为 404。IP 候选规则先确认当前管理员不会自锁，随后事务 CAS 发布；来源地址始终取平台请求客户端，设备与串口目标地址不参与匹配。

接口字段与前端交互不变。提交结果未知沿用 503 和“先查询最新状态”的提示，不能承诺非幂等 PATCH 自动重试。业务配置与成功审计之外，失败请求仍由统一访问日志记录。

## 验证与清理

新增单元回归先在旧路由证明写入/审计缺少事务 session，再验证同 session 传递以及陈旧版本、自锁和重名拒绝不会添加成功审计。MongoMock 仅验证接口和状态语义，不模拟回滚。

`scripts/verify_admin_audit_transactions.py` 使用真实副本集随机数据库、`create_app` 正式路由及 `httpx.ASGITransport`：审计故障返回 503，平台首次配置/节点插入/节点更新/IP 策略全部回滚；恢复后同版本重试只留一条审计；同版本四并发恰好一个成功，其余 409；自锁和陈旧版本无成功审计。无需 Worker，也不连接任何设备。

真实脚本首次可运行时路由已经修改，未宣称执行过旧实现的真实数据库 RED；RED 来源是独立单元回归。验证和本机部署、CI 的最终结果记录在当前状态总表。

最终真实脚本明确使用会改变匹配集合的候选策略：从原来的 `/24` 收缩为当前管理员 `/32` 并新增原拒绝来源 `/32`。注入失败后，原同网段另一来源仍为 200，原拒绝来源仍为 403；成功重试后它们分别切换为 403/200，证明策略只在事务成功后生效。

首次脚本运行曾将派生服务日志写入临时目录的父目录，已改为 `TemporaryDirectory/logs`，使 API 的 `service-logs` 也在可回收目录内部。按来源、时间和文件清单核验后清理唯一自建残留日志 18,846 字节；修订后复跑并确认旧路径不存在。本机正式日志、设备数据和管理员配置均未修改。最终临时数据库、客户端和目录已由 finally 回收。

本地全量后端 627 项、前端 47 项、前端构建、Ruff 与 diff 检查通过。正式 API 真实副本集回滚/并发/来源切换全部通过，验证脚本已纳入 container-smoke。

## 后续边界

独立审查确认 `tasks/api.py` 的控制操作仍依次取消旧 operation、插入新 operation、更新任务及部分运行锁/run，再写审计。中间故障可留下不一致控制状态，这是下一完整模块；事务内重读还须结合资源删除并发验证，不能仅凭快照读取宣称避免写偏差。

任务创建包含自动启动，不能只替换外层幂等入口而遗漏 operation 与启动意图。登录/退出还需将会话写入、旧会话撤销与审计一起提交，Cookie 仅在提交后设置。手动命令准入、定时预算、发送领取已完成，外层审计需补齐但不要重做这些事务。
