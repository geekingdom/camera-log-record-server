# API异常生命周期清理

## 问题与修复

持续目标复核发现，API在进入清理保护前就创建Mongo客户端、Repository和日志监听器。日志目录初始化或Repository构造抛错时，已经取得的客户端不会关闭；Mongo关闭抛错时，随后日志监听器的停止也会被跳过。Worker已有嵌套清理，不需要重复改造。

`backend/camera_logs/main.py`现在将资源取得纳入生命周期的try范围，并以嵌套finally保证数据库关闭异常后仍执行日志排空。注入数据库的所有权不变，只有本实例创建的客户端才会关闭。正常顺序仍为后台任务、节点HTTP池、Mongo、日志；多重失败保留Python异常链，不静默吞掉错误。

## 验证

- `tests/test_api_lifespan_cleanup.py`先在旧代码复现3项失败：日志初始化失败、Repository构造失败、Mongo关闭失败。
- 修复后新增测试与Worker生命周期、节点HTTP池、结构化日志、请求记录和来源边界33项通过。
- 独立只读审查核对资源所有权和关闭顺序，API相关9项通过；Ruff和差异检查通过。
- API修复后后端全量1480项通过（162.38秒），包括连接保活、空闲重连、行前缀及归档既有回归。
- 无设备连接、日志采集任务、下载或持久数据库写入；测试替身及临时目录不包含真实设备日志。

该证据证明应用按异常分支调用资源收尾，不代表物理主机断电后能够排空内存日志，也不替代目标集群故障验收。
