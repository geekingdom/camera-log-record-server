# 节点写入延迟阈值验证

日期：2026-09-15。

## 目标与语义

节点写入延迟从固定200毫秒调整为管理员保存的逐节点配置`writeLatencyLimitMs`。登记默认值为200，允许严格整数1至60000。历史节点和旧心跳缺字段继续采用200。

- 达到有效上限的75%时节点健康状态预警。
- 仅延迟**超过**上限时拒绝新的采集会话；等于上限仍可准入。
- 高延迟不停止现有采集任务、不关闭连接、不丢弃已进入有序写入队列的日志批次。
- Worker下一次心跳重新读取配置并更新本地准入；调度候选和领取事务均再次使用保存配置，防止管理员编辑与领取之间出现旧阈值窗口。

该配置只控制新会话准入。它不改变日志字节顺序、批量I/O、同步频率、部分写入处理和永久磁盘故障边界，也不能提高实际磁盘或网络吞吐。

## 验证

`scripts/verify_node_write_latency.py`连接真实Mongo副本集并在结束时删除随机测试数据库，结果如下：

```json
{"passed": true, "configurationConflictRejected": true, "relaxedLimitClaimed": true, "nodeLimitsIndependent": true, "noPartialRunOrLock": true}
```

验证过程先使用500毫秒阈值和350毫秒采样，在领取事务写栅栏处将配置收紧至200毫秒，确认新任务被拒绝且没有遗留`runs`或`endpoint_locks`；随后恢复500毫秒，同一心跳即可领取。另以250毫秒采样分别验证缺省200毫秒节点拒绝、独立500毫秒节点允许，证明阈值不会跨节点串用。

同时通过：后端全量1464项；本轮Ruff和`git diff --check`；前端31个测试文件158项、生产构建，以及20项生产页面浏览器脚本。隔离真实API/Worker/WebSocket/小时下载冒烟通过，随机数据库和临时日志已清理。

本机运行服务通过正式管理员PATCH把`local-dev`从200改为500毫秒，实际Mongo心跳与公开节点API均读取到500；再改回200，两处均确认恢复。任务数始终为0，未连接实体设备或注入虚构延迟。配置更改无需重启；已有`accepting=false`心跳需等待Worker下一心跳刷新，不能承诺所有节点瞬时传播。

浏览器验证覆盖登记默认值、确认保存、编辑回填、PATCH字段、节点卡片“写入延迟/上限”展示以及1440和390像素布局。

## 剩余验收

本机真实Mongo验证和前端构建不等同于生产容量结论。目标Linux多节点环境仍需依据实际磁盘、压缩积压、网络及源端速率标定阈值，并完成500路每路1200行/秒持续24小时、独立文件可读延迟和混合下载负载验收。
