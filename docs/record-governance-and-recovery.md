# 高增长记录与受控恢复使用说明

本文说明四项持续运行功能的配置、运行边界和排障方式。它们保护的是新任务分配、MongoDB 中会持续增长的元数据、实时页面的可补读范围以及已过期导出目录；设备原始日志和 coredump 内容仍由 Worker 文件系统管理，不写入 MongoDB。

## 节点输入速率准入

管理员在服务节点配置中设置 `inputRateLimitMiB`。新登记节点默认值为 `50`，单位是 MiB/s，`1 MiB = 1024 x 1024 bytes`；取值 `0` 表示关闭该节点的输入速率准入。历史节点、未登记节点及缺失该字段的配置也按 `0` 处理，避免升级后意外拒绝原有环境。

节点当前输入速率达到或超过阈值时，调度、任务领取和 Worker 建连前检查都会拒绝为该节点分配新的采集任务。该规则只影响新分配，已在采集的任务不会因节点达到阈值被停止。启用了限制但指标缺失、不是有限数或为负数时，系统保守拒绝新的分配，待节点恢复有效心跳后再参与调度。

该值是准入保护阈值，不是单节点或集群的容量承诺。应结合 CPU、内存、磁盘写入延迟、网络速率和真实设备日志特征逐步调整。调低阈值只会影响后续分配，不会主动迁移或中断已有连接。

## 增长记录保留

后台配置 `recordRetention` 分别管理审计、运行事件和已结束运行的历史：

| 字段 | 默认值 | `0` 的含义 | 处理对象 |
| --- | ---: | --- | --- |
| `auditDays` | 90 天 | 关闭审计自动维护 | `audit` |
| `eventDays` | 90 天 | 关闭运行事件自动维护 | `events` |
| `runDays` | 90 天 | 关闭运行与终态明细维护 | 已结束 `runs`、终态命令/操作及预算 |

维护循环每5秒读取一次已保存的平台配置，单轮最多运行30秒。它使用 `record_archive_maintenance` 租约、owner、revision 和持久 keyset 书签保证多实例不会推进同一批数据；每一轮最多处理100个运行候选以及每类100个审计、事件或操作候选。维护失败或进程取消后不会从内存位置续跑，而是在下一轮从数据库书签和当前引用状态继续检查。

运行归档不会把全部历史命令一次装入内存：每个事务最多处理100条命令或预算，摘要写入 `run_archives`，待全部子批次完成才删除对应 `runs`。摘要只保存有界的计数、状态和时间，不保存命令正文或无界 ID 列表。审计删除时会把 `id`、操作者、动作、目标、请求 ID、结果和创建时间压缩至 `audit_archive_chunks`；每个 UTC 日每100条一块 gzip，块固定保留365天。`record_purge_days`保存按集合、UTC 日聚合的删除计数，用于观察维护进度，不保存已删记录正文。

下列记录不会因为超过保留期直接删除：活动任务、未结束运行、非终态命令或操作、`UNKNOWN` 发送、未结算预算、有效或永久幂等映射、端点锁，以及仍被当前任务控制操作引用的记录。候选项会在事务内重新读取并检查这些保护条件；审计摘要、日计数与源审计删除也在同一事务内提交。MongoDB TTL 只用于认证记录、请求事件和短期快照等无恢复依赖的数据，不能代替上述保护判断。

## 实时日志缺口补读

实时页面收到连续字节范围之间存在缺口时，会依据缺口两端的文件、偏移和会话锚点查询已登记的日志目录，随后按目录顺序读取已持久化字节。该过程不会声称恢复设备从未发送到平台的数据；跨会话边界也只证明文件可以顺序读取，不证明设备端输出连续。

为避免一次缺口查询扫描过多元数据，首次定位的两端时间跨度最多24小时，目录最多500个文件，且最终范围最多200个文件片段。任一上限超出时，接口返回不可补读原因，页面应引导用户缩小范围或使用小时归档读取，而不是在实时内存缓冲中继续扩大快照。

分页游标保存于 `log_gap_snapshots`，其中只有任务 ID、签名后的目录定位信息和续页位置，不含日志正文；快照一小时 TTL，到期后必须重新定位，不能用新目录混入旧缺口。前端仍需按文件、偏移和会话去除传输重叠后再解码显示。目录缺失、两端顺序无法定位、已确认字节水位不足时，均明确返回无法补读原因。

## 异常导出产物回收

下载和导出产物保存在节点的 `exports/` 或 `exports/.tmp/`。维护器只处理属于本节点、已到期、终态为成功/失败/取消/过期、启用了输出锁协议且具备输出归属信息的作业。未知旧目录、缺少元数据、仍在写入且没有安全关闭证据的目录一律保留，避免将进程崩溃窗口内可能仍被旧写入者使用的目录误删。

清理前先在作业记录上 CAS 到 `CLEANING`，移除过期读者令牌并确认没有活动读者；下载读者取得同一条作业记录上的短租约，读取中持续续租。之后清理器必须取得 `exports/.locks/<jobId>.lock` 的非阻塞 `flock`，才可以删除目录。进程死亡时内核会释放 flock；若记录仍停在过期的 `CLEANING`，维护器先恢复为可再次领取状态。清理完成后才写入 `CLEANED` 与完成时间。

这套协议允许多个下载和维护请求并发运行：活跃读者会阻止回收，写入者和清理者受同一文件锁互斥，取消维护时会等待已有删除线程结束，防止同一路径并行执行多个删除。目录包含软链接、路径逃离日志根目录或状态无法确认时会拒绝处理。旧产物保守保留是设计行为，需要人工确认其归属和关闭证据后再单独处理。

## 验证范围

`scripts/verify_growth_records.py` 已在本机真实 MongoDB 副本集验证增长记录的事务回滚、1001条命令的分段归档、维护租约互斥，以及 `runs`、`commands`、`idempotency`、`operations`、`jobs` 五类查询的 Explain 路径。脚本使用随机数据库并在 `finally` 中删除，不连接真实设备，也不读取或删除真实采集日志。五类样本查询均以10条返回上限验证受限扫描，检查结果包含10个以内的 keys/docs 扫描和无阻塞 `SORT` 的索引计划。

这些证据只证明本机真实 Mongo 的事务、租约、分段和索引路径能够工作，不能证明500路、每路1200行/秒运行24小时的生产容量，也不能替代长期索引体积、低选择性筛选、副本集复制延迟、多节点下载和真实设备日志特征的验收。生产部署后应持续监控集合大小、索引大小、维护每轮耗时、受保护候选数量、清理失败数和副本集延迟，并在真实数据分布下重新执行 Explain 抽样。
