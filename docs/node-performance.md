# 逐节点性能预算与通用写入优化

## 需求与实现范围

所有节点采用同一实现，不以任何单台服务器的总核数、503GB内存或千兆网络作为固定基线。管理员配置AUTO或MANUAL模式及缓冲、写入并发、批量、最长批等待、后台读取预算；节点根据容器CPU/内存硬限制与宿主压力应用自身预算。已有容量、输入速率和写入延迟准入阈值保持独立，不由控制器修改。

采集写入使用专用有界线程执行器，正文、时间索引与fsync可分别观察；时间索引句柄复用。接收前预留最坏前缀空间，按应用字节预算背压；缩小预算等待旧数据排空，不丢弃正文、不重试结果未知写入。预算不包含SSH/Telnet库、操作系统socket缓存和页面缓存，因此不是整个进程RSS上限。

控制器使用持续样本、冷却和稳定窗口调节，未知指标不能支持放大。采集顺序、每秒必要fsync、停止收尾、原始归档和日志保留合同不变。采集线程取消必须等待实际磁盘操作结束。

## 后台工作

搜索、快照和日志复制复用节点读取预算。持续压力下，新开始的压缩作业按降低后的预算节流原文压缩输入，并暂缓可重建的全文索引；当前已经进行的原子归档不强制中断。压缩继续单进程执行，避免未经目标磁盘验证盲目放大并发；恢复后补建旧索引。目录清理不因压力跳过，避免归档积压进一步占满磁盘。

压力下的压缩预算覆盖原文和索引摘要、打包复制、归档正文复核；按逻辑读取字节计费，不等同物理硬盘吞吐。父进程以单执行槽维护归档优先队列，直到实际获得执行机会才读取当前预算；正在执行的原子归档不强制中断，后续排队作业可以使用恢复后的预算。有归档积压或性能压力时暂缓内联全文索引，归档校验发布和子日志清理不等待索引；既有后台维护补建缺失索引，搜索仍可回退原文精确扫描。已经运行的索引不强制抢占。

压缩和查询属于独立进程，预算不是跨进程的磁盘总带宽限额；Mongo、NFS接收及其他工程I/O仍需要操作系统与部署资源隔离。直接Coredump下载和网络出口也不由此预算统一限速。归档读取预算为1MiB/s时，600MB原文的摘要、压缩复制及正文复核三轮约需29分钟，索引、既有包合并、压缩CPU与同步落盘还会增加耗时；不能把该预算理解为600MB只读取一遍。

当前不引入Redis/Kafka，不自动迁移冷热路径，不执行启动磁盘压测，不承诺持续超负载下无限接收。TCP背压只能减慢发送；设备无持久化重放能力时，超过其自身缓冲的持续超负载仍存在源端丢失风险，应通过容量和故障缺口验收识别。

## 配置与生效

节点配置查询会实时给出只读`performanceRecommendation`，依据该节点已上报的新鲜有效CPU、可用内存和容器限制计算保守起点。节点编辑窗口展示推荐值与探测依据，点击应用推荐仅填表，可继续修改，保存确认后才改变配置；刷新推荐不会自动覆盖草稿。尚未收到心跳、节点离线或遥测不足时不能一键应用推荐。

推荐不以总内存代替空闲内存，也不推测磁盘型号、实测IOPS或其他工程未来负载。它不会自动提高任务容量、输入准入或写入延迟上限。保存值、推荐值和当前实际有效值分别展示：即使手动设置更大的预算，Worker仍执行现有硬资源安全约束。

推荐规则：有效CPU核数向下取整后限制在1至8路写入；缓冲按可用内存的1/16计算并限制在16至256MiB。有效CPU不超过2核或可用内存不超过512MiB时推荐64KiB批量、10MiB/s后台读；至少8核且可用内存至少4GiB时推荐256KiB批量、50MiB/s后台读，其余推荐256KiB和25MiB/s。最长批等待均为100ms，默认建议AUTO；用户可改成MANUAL。低于64MiB可用内存不推荐，以免合法表单最小值高于运行时安全缓冲上限。

管理员在后台配置的节点准入模块中登记或编辑节点，保存性能策略；Worker下一轮心跳读取后生效，不要求修改多个部署文件或重启采集任务。节点看板显示实际有效值、降级原因、缓冲积压和写入阶段P99。未升级的Worker不会执行新策略，应同时部署API、Worker与前端。

| 配置 | 默认值 | 可配置范围 |
| --- | --- | --- |
| 模式 | AUTO | AUTO / MANUAL |
| 应用接收缓冲 | 64MiB | 16至4096MiB |
| 写盘并发 | 4 | 1至32 |
| 批量目标 | 256KiB | 16至1024KiB |
| 最长批等待 | 100ms | 10至200ms |
| 后台逻辑读取 | 50MiB/s | 1至200MiB/s |

两种模式均受实际可见CPU配额、亲和性和可用内存约束。缓冲最多占探测可用内存的四分之一；未知内存拒绝新会话并保留2MiB最小读取预算，已有数据不因缩容被丢弃。该下限不等于保证操作系统不会OOM。

AUTO连续3个高压样本后降低后台读取；仅CPU或内存高压才同时降低写并发，纯写入延迟不会减少写并发。后台降速使用实际写入排队和执行耗时，不包含主动批等待；原接收到可读的总延迟仍用于准入和展示。磁盘空间占用不是I/O延迟信号，不再单独降低后台读取，磁盘容量告警和新任务准入限制继续生效。压力原因分别标明CPU、内存、写入延迟。

两次自动调整至少间隔30秒，CPU与内存均有效且连续稳定60秒后恢复剩余差额的一半，至少增加1，不超过管理员与资源上限；例如1MiB/s向50恢复为26、38、44、47、49、50，需持续稳定约6分钟，不再需要49次一分钟恢复。批量与最长等待按保存值热更新，不声称自动寻找最优批次。单节点容量、输入速率和写入延迟准入阈值不会自动提高。

节点看板分别展示归档排队与执行数量及各自最长耗时，`pendingJobs`保留表示未完成总数，`oldestSeconds`包含排队至完成的总时长。旧Worker未拆分阶段时仅显示未完成数量，不把它冒充正在排队。5分钟告警是处理时长提示，不是采集失败，也不触发丢弃日志。上述阶段指标仅保存在内存与覆盖更新的节点心跳中，不增加Mongo历史集合或索引。

写入样本区分批次等待、执行器排队、正文追加、时间索引追加和两类fsync；每项仅保留最近1024次样本。它们不是源端发送到可检索的全链路P99，也不能直接代替文件可读P99验收。

## 写入延迟告警的解释

`writeLatencyMs`是本节点各活动会话中最慢的最近60秒P99与未完成批次等待年龄的最大值，包含主动批等待、写入排队及执行，不是设备网络往返时间。新增`performanceStatus.writeIoLatency`单独统计`write_many`调用的排队及执行，排除主动批等待与后续WebSocket发布，包含必要文件轮转和写入同步等待。两类P99分别计算，不能直接相减得到另一个精确P99。

阈值默认200ms，管理员可配置1至60000ms；这是软件校验范围，不代表建议设置60秒。超限暂停新会话准入（含需要重新领取的任务），已有采集器不会因该告警被主动断开。AUTO还根据实际写入压力限制后台读取。提高阈值不增加磁盘吞吐、不使已有写入更快，也不能保证持续过载的完整性。应用缓冲有界，耗尽后通过背压减缓读取；设备自身缺少可持久重放缓存时，持续过载仍可能导致源端丢失。

原直方图在超过1秒后取下一档2的幂，例如1100ms上取整为2048ms。现在1秒内按1ms、1至60秒按100ms上界，更长故障才用幂次桶，仍不低估已观测延迟。页面显示2.0秒时应同时查看实际I/O的P99、pending、批次等待、写执行器排队和fsync阶段，而不能凭高CPU/大内存排除共享磁盘、容器存储、同步落盘或其他服务争用。没有宿主机I/O证据时不把这些候选当作已确认根因。

## 验证要求

覆盖不同CPU配额、cgroup v1/v2内存、宿主可用内存、未知遥测、时钟回拨、冷却恢复、配置热更新、并发收缩、取消收尾和源端逐路摘要。合成验证的性能数据只代表本机短时结果，目标Linux多服务混合负载及24小时500路容量仍单独验收。
