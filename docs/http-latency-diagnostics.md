# HTTP 读取延迟诊断

## 范围与结论

2026-09-09 本机运行 API、Worker、MongoDB 和合成负载源。每轮 64 路 Telnet 串口，
每路 1,200 行/秒、256 字节/行，持续 60 秒，每路一个实时订阅并同时读取内容 API。
这些诊断没有并发搜索，不能替代联合负载或 500 路持续 24 小时验收。

实测发现压测客户端在发送请求前存在秒级等待；固定分池明显缩短了这段等待，
但逐路可读 P99 仍不满足 200 ms。不得用客户端改善、服务端计时或正文完整性通过
代替容量验收通过。各次运行同在开发机，未做统计重复与硬件隔离，不宣称精确加速比。

## 定位与实现

HTTP 阶段计时从原请求开始累计，记录 `connect_tcp`、请求头发送、响应头接收及正文
接收的开始与完成事件，不保存认证信息和设备正文。一个慢请求总耗时 5,348.878 ms，
首个建连事件发生在 5,105.367 ms，建连完成为 5,115.295 ms。主要额外等待发生在
网络发送前，不能归因于设备写盘或 TCP 建立本身。

原压测入口使用 `httpx.Limits(max_connections=max(32, routes + 8))`；该显式配置的
`max_keepalive_connections=None`，实际空闲上限受总连接数约束，不能误认为默认 20。
新 `service_benchmark_http.py` 把同一总额平均拆分到八池，HTTPX 客户端仍负责认证、
超时及正文流，传输层透传完整 Request 并直接返回 Response。开始关闭后拒绝新请求，
部分初始化失败或某池关闭失败时继续释放其余已进入的池，不新增重试。

分池对照仍观察到 API 目录查询 P99 61.366 ms、节点查询 65.090 ms、上游调用
227.881 ms；节点文件 IO 为 5.970 ms、读取队列为 17.349 ms。上游调用包含节点阶段，
不能重复相加。下一步应测量服务端调度与查询开销，并在改进后重新运行联合搜索负载。

本轮没有替换 API 或 Worker，也没有发送真实 debug 命令；真实设备连接与合成压测隔离。

## 最终代码验证

落地后的 `.local/service-node-diagnostic-64-client-shards-final/` 收齐并校验同样的
4,608,000 行，目标发送速率、实时、下载正文和清理通过。21,794 次内容请求的发送前
等待 P99 为 16.809 ms，请求 P99 为 334.168 ms，最慢一路可读 P99 上界为
1,365.312 ms，仍超标。全路共同发送窗口为 53.286 秒，低于 60 秒场景的 57 秒要求；
启动阶段多次出现 Telnet 环境选项协商等待提示，启动偏差与容量门槛仍需进一步定位。
不能将这轮称为并发验收通过，也未延长计时或降低窗口标准来改写结果。

本地后端 533 项、前端 25 项、Ruff 与生产构建通过。新增测试覆盖不同路数下连接预算、
并发请求正文与认证、Range 和流式响应、部分初始化失败、关闭失败、取消、禁止重试及
关闭后拒绝复用。结束后 `local-dev` 的活动任务恢复为 2、容量仍为 100；34、35 保持
原运行实例且为 `COLLECTING`。所有压测报告和日志正文留在忽略目录中。
