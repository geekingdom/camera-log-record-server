# MongoDB 增长型记录保留策略

设备日志正文、小时归档和 NFS coredump 源文件保存在 Worker 文件系统，不进入 MongoDB；MongoDB 保存任务配置、文件目录、认证历史和排障元数据。认证历史、审计事件、运行事件、命令执行记录和操作记录会随运行时间增长，因此按集合分别治理，避免一个全局 TTL 误删仍用于恢复的记录。

## 默认行为

认证历史默认按90天（约三个月，不是日历月减法）保存，新记录写入绝对过期时间；Mongo TTL 异步删除，接口会先隐藏已过期记录。`AUTHENTICATION_RECORD_RETENTION_DAYS=0` 时新记录不写过期时间。配置变更不修改旧记录已经保存的过期时间；升级前没有 `expiresAt` 的历史记录需执行下文回填，查询会先按当前90天策略限制可见范围。其它增长型业务记录默认永久保留，请求排障事件保持固定30天 TTL。

## 长期增长分层

每个会持续产生记录的集合必须先归入下列一层，再允许写入正式库。不能把设备日志正文、协议收发字节、实时展示行或 coredump 内容放入 MongoDB；它们由 Worker 文件系统的小时归档、文件目录和下载任务管理。MongoDB 只保存足以定位、查询、审计和恢复的元数据。

| 层级 | 集合或记录 | 当前治理 | 查询与容量边界 |
| --- | --- | --- | --- |
| 配置与当前状态 | `resources`、`tasks`、`nodes`、`node_configs`、模板和用户 | 永久保存；软删除记录保留删除时间与创建人 | 以稳定 `id`、资源关联和状态索引读取；不保存每次状态轮询的副本 |
| 可压缩历史 | `authentication_records`、未来的周期性健康汇总 | 认证成功按资源、UTC 日和身份连续区间聚合，90 天 TTL | API支持 `createdAt,id` 游标，当前前端仍使用页码；一次认证区间存首末时间与次数，不逐次展开 |
| 有恢复依赖的事件 | `commands`、`operations`、`budgets`、`runs`、任务运行事件 | 默认永久保存，尚未启用自动删除 | `UNKNOWN` 命令、隔离、预算和接管判断完成前不得按终态 TTL；先定义可重建的归档摘要及恢复引用窗口 |
| 审计与排障事件 | `audit`、`events`、`request_events` | 请求事件固定 30 天 TTL；审计和运行事件目前只生成候选保留计划 | 管理页必须限定时间范围、稳定排序和最大返回量；事件正文不得保存密码、令牌、命令密文或日志正文 |
| 短租约及临时产物 | 登录会话、幂等键、下载会话、导出/快照 claim 与产物 | 以 `expiresAt` TTL 或既有租约收尾 | TTL 只负责无业务依赖的临时数据；物理文件删除须由拥有者确认，不能仅依赖 TTL 回调 |

认证记录只是这一策略的第一类落地对象。新增类似“每分钟探测”或“周期性巡检”功能时，默认采用固定时间桶、连续状态边界和计数汇总，保留状态变更、失败、人工操作及设备身份变化的单独事件。每个桶必须保存首见、末见、次数、版本和不可变过期时间；不能通过更新 TTL 让长期连续成功的单条记录永久存在。

## 写入、查询与归档门槛

高频记录的设计先以记录数、平均 BSON 大小、索引数和保留天数估算容量，而不是仅以业务功能判断是否入库。设计评审至少记录以下预算：

- 峰值写入速率与正常写入速率，包括 API 重试和 Worker 并发写入；认证成功聚合后应按“资源数/日”而非“探测次数/分钟”估算。
- 单条文档与每条索引的实际大小。索引不是免费副本，新增一个复合索引会同时增加每次插入、更新和 TTL 删除的写入成本。
- 默认列表、筛选和导出的最大时间范围、最大页大小和是否需要精确总数。深分页不得用不断增大的 `skip`；优先游标、按需总数或异步统计。
- 线上样本的 `explain("executionStats")`、慢查询、索引大小和副本集复制延迟。临时库 `IXSCAN` 仅是候选索引信号，不是长期容量验收。

当某类有恢复依赖的记录达到业务确认的保留窗口后，采用“先摘要、后分批删除”的两阶段方案：先把可长期查询的聚合摘要或导出清单写入独立集合/对象存储，完成恢复引用检查和抽样还原验证，再按稳定时间键、限量批次删除原始终态记录。删除作业要记录开始/结束时间、查询条件、删除数量、错误和恢复依据，并提供预览模式；不得在 API 请求内执行大范围 `delete_many`，也不得把 TTL 当成归档成功确认。

运行事件目前兼容旧 `detectedAt` 并在读取时派生 `_eventTime`，所以即使已有筛选索引，也不能声称其所有排序路径都已无阻塞排序。后续统一新增写入的展示时间字段、完成旧数据迁移与真实 `explain` 验证后，才可以将管理事件改为游标分页并评估按时间分区或摘要归档。对审计记录同样先保证操作可追溯，再由管理员配置经审批的保留期；当前 `AUDIT_RECORD_RETENTION_DAYS` 仅是候选计划，不会自动删除数据。

## 连接原因事件的增长预算

`IDLE_TIMEOUT`、`READ_ERROR`与`CONNECTION_GAP`复用`events`，仅在状态变化时写入，不按设备日志行数写入；使用已有taskId/nodeId/type与createdAt索引，不新建同类索引。原因事件仅保存任务/运行/会话/节点、固定说明和结果等级，不保存设备正文或原始错误文本。正常稳定连接没有这类周期写入。

持续异常仍有增长成本：以500路均每10秒触发一次空闲阈值粗略估算，不计登录/退避时间时，每类每天约432万条；原因加通用缺口两条记录约864万条。实际速率受连接、初始化和重试时间影响。该估算不是容量验证；部署须结合真实BSON、索引和复制成本监测。当前运行事件没有自动保留执行器，后续分类清理必须保留仍用于隔离及恢复的证据，不能给整个events集合直接统一TTL。

## 连续成功聚合

仅合并同一资源、同一UTC自然日内连续的周期认证成功，要求型号和序列号一致且没有身份变化。首次认证、手动认证、编辑认证、失败和身份变更均独立保存，也会中断前后的成功区间。按日分段意味着持续成功时仍每天新建一条，这能固定到期时间并避免无限延长历史寿命。每分钟一次探测的稳定设备，通常从每天1440条周期成功记录减少为每天1条；实际条数受失败、变更和人工操作影响。

聚合条目的 `createdAt` 是该段首次认证时间，`latestAt` 是最近一次时间，`occurrenceCount` 是整段累计次数；`id`、首次时间和 `expiresAt` 不随累加改变。连续边界以同一资源认证结果的数据库提交顺序定义，避免并发探测中较早完成但较晚到达的成功结果拆分桶；`latestAt` 始终取最大的设备观测时间。筛选时间区间时，返回与该区间相交的整段记录，次数不是所选子区间内的精确次数。旧记录没有聚合字段时按一次认证展示，不从旧数据推测补造次数。身份字段允许为空，按空字符串统一比较。

`authentication_record_heads` 每资源固定一条，以资源ID作为Mongo主键，保存最新事件指针和递增代次。每次认证在同一事务内先写该头记录，再插入或累加历史；并发写冲突会重试，避免失败插入与成功累加写入不同文档而跨过状态边界。迟到的完成时间不会回写到已有成功区间。该头集合随资源数量增长，不随认证次数增长，不能对其设置与历史相同的TTL。

## 已落实索引

| 集合 | 主要查询路径 |
| --- | --- |
| `authentication_records` | 资源ID，结果/身份变更的可选组合，`createdAt,id`稳定倒序；`expiresAt` TTL |
| `audit` | 默认`createdAt,_id`倒序，action/actor/targetId/requestId筛选与同样排序 |
| `request_events` | 默认时间倒序，taskId/httpStatus/route/clientIp/requestId筛选与稳定排序；保留30天TTL |
| `events` | taskId/nodeId/type/requestId筛选及时间；派生时间排序限制见下文 |
| 任务、文件、作业、命令 | 保留既有调度/领取、任务小时、作业租约、命令预算及历史查询索引，没有盲目新增重复索引 |

事件索引集中在 `common/event_indexes.py`，认证与既有索引在 `common/database.py`。2026-09-11本机数据库已实际安装新增索引，15条无过期时间的旧认证记录完成回填，复跑待处理数为0。旧前缀索引保留，不能只因新复合索引有相同前缀就无依据删除。

## 升级已有数据

索引由 API/Worker 的 `Repository.initialize()` 幂等安装。旧认证记录缺少过期时间或值为 `null` 时，部署后在工程环境执行：

```sh
python scripts/backfill_authentication_expiry.py
python scripts/backfill_authentication_expiry.py --apply
```

第一条仅预览；第二条每批最多500条读取并逐条补齐 `createdAt + AUTHENTICATION_RECORD_RETENTION_DAYS`。单次默认最多5000条，可用 `--max-records` 调整（最高100000）；结果 `limitReached=true` 时继续运行直至没有待处理记录。使用工程 `.env` 中的数据库配置；不打印凭据，不覆盖已有过期时间，不修改日志、core或其它集合。过期记录随后由Mongo TTL删除，因此该迁移是应用90天保留策略的操作。中断后可以重跑，已处理记录不会再次改写；保留配置为0时工具拒绝执行，避免意外给永久记录设置到期时间。大库迁移由单个维护进程在低峰分批执行，当前没有全局迁移租约。

## 可配置项

| 配置项 | 集合 | 时间字段 | 默认 | 清理边界 |
| --- | --- | ---: | ---: | --- |
| `AUTHENTICATION_RECORD_RETENTION_DAYS` | `authentication_records` | `createdAt` | 90 | 默认仅保留最近三个月；认证记录同时写入 `expiresAt` 并由 TTL 索引清理 |
| `AUDIT_RECORD_RETENTION_DAYS` | `audit` | `createdAt` | 0 | 按用户操作时间清理 |
| `RUNTIME_EVENT_RETENTION_DAYS` | `events` | `createdAt` | 0 | 按运行事件时间清理 |
| 固定 TTL | `request_events` | `createdAt` | 30 | 由请求事件 TTL 索引治理；修改该期限需要索引迁移 |

## 查询和清理原则

认证新记录会写入固定 `expiresAt` 并由 MongoDB TTL 自动过期；连续成功聚合不会更新该字段。`common/record_retention.py` 对审计和运行事件目前只生成预览查询计划，未连接自动删除作业。后续维护按每批最多1000条设计，并记录集合、截止时间和删除数量；不能将预览计划解释为已经生效的自动保留功能。命令、操作、预算、幂等映射和运行记录仍保留，待完成所有恢复引用审计后再设计清理。

清理应与恢复流程协调：命令的 `UNKNOWN` 结果、操作的失败/取消终态和认证变更历史是排障证据，默认保留；如果业务需要缩短期限，应先导出审计摘要并在低峰分批执行。MongoDB TTL 适合无业务依赖的请求排障事件，不适合活动状态或需要事务判断的集合。

## 增长集合 Explain 验证

`scripts/benchmark_db_growth.py` 在随机数据库中生成认证历史、审计、运行事件和请求
事件样本，对代表性首屏和深分页执行过滤、排序和分页，并输出 Mongo
`executionStats` 中的 `plan`、扫描键数、扫描文档数和耗时。脚本结束时删除随机库；
`--compare-indexes` 只在该临时库创建候选复合索引，绝不会修改线上索引。

```sh
python scripts/benchmark_db_growth.py --rows 20000 --compare-indexes \
  --output output/db-growth-$(date +%Y%m%d%H%M%S).json
```

报告出现 `COLLSCAN`，或 `totalDocsExamined` 明显大于 `nReturned`，应结合线上数据
评审过滤字段、排序字段的复合索引；`IXSCAN` 只证明该次样本选中了索引，不能代替
生产数据规模、写入压力和索引占用验收。MongoMock 没有真实查询优化器，单元测试仅
验证报告解析和分页契约，不能作为索引命中证据。认证历史优先使用资源 ID、时间和
ID 的游标分页，避免无限增长集合使用大 `skip`；总数统计应按需关闭或异步化。

## 新集合与流程约定

- 建集合时同时记录增长速率、记录大小、保留期、是否被任务恢复或幂等映射引用，避免先无限写入再补清理策略。
- 根据实际查询的等值字段、范围字段、排序和稳定次排序键建立复合索引；必须覆盖默认列表，不能只优化带筛选的页面。
- 针对每个可选字段组合建索引会放大写入与磁盘成本。优先常用路径，使用真实Mongo `explain`核对扫描量和阻塞排序，再决定新增索引。
- 同规格索引升级保留旧名字，检查TTL和partial/sparse等选项；多进程重复初始化必须可复用，不能无条件删除旧索引。
- 事件或计数压缩必须有明确的连续状态边界及并发串行点；失败、身份变更和用户操作不能被成功聚合覆盖。
- TTL不提供准点删除保证，查询需考虑可见性；有预算、租约、幂等和恢复引用的记录不得仅按终态直接TTL删除。
- 普通子串或忽略大小写的正则搜索无法指望普通B-tree索引消除全扫描；规模增长后应单独评估搜索索引和查询限制。

运行事件为了兼容旧 `detectedAt`，正式接口计算 `_eventTime` 后排序。新增过滤索引能缩小候选集，但不能直接消除这个派生排序；带结果/级别的派生筛选也不能仅凭普通find基准宣称已完全优化。未来统一写入时间和展示字段后再迁移查询，不修改历史事件语义。
