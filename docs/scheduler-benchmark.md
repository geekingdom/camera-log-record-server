# 批量调度基线

调度器在单一调度租约内，通过一次仅包含 `nodeId` 的任务投影查询汇总占用，所有未释放归属都计入集群容量，包括失联节点。只有任务领取成功才递增本周期占用；并发停止释放出的容量保守地留到下个周期使用。每个待分配任务仍重新检查节点心跳、磁盘、写入延迟和准入开关，节点中途停用后不继续分配。

该统计依赖现有单调度者租约，不支持绕过 `scheduler_loop` 并发调用 `schedule_once`。它没有把计数快照变成跨多个独立调度者的原子容量预留，也不替代失联节点的基础设施隔离。

## 本机测量

运行 `.venv/bin/python scripts/benchmark_scheduler.py --output .local/scheduler-check.json`。脚本使用当前 MongoDB 连接配置，但创建随机临时库并在结束时删除，配置八个虚拟节点、每节点容量 100 和 500 个待分配任务。它只执行元数据调度，不启动采集节点、不连接设备、不操作主库。输出路径已存在时拒绝覆盖，报告不包含连接凭据。

当前基准创建十秒租约并向每次领取传入 owner/fence，执行与正式调度相同的八秒周期超时。2026-09-09 单任务事务改造后，500 项均在 3,580.812 ms 内领取成功，单节点最多 63 项，产生 500 次事务提交。证据在 `.local/scheduler-transactional.json`。事务内仍逐项检查节点与任务，并把运行锁、任务归属和运行记录合并提交；不再为这三项写入分别等待日志持久化确认。本机单次结果不代表所有环境的时延或 500 路持续日志容量。

## 计数优化历史对照

以下结果属于单任务事务改造之前，旧脚本直接调用 `schedule_once`，没有传入调度租约或强制八秒超时，不应与当前基准混为同一测试范围。

2026-09-09 同机单次前后对照，MongoDB 客户端与正式 API 一致，使用 `w=majority` 和 `journal=true`：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 调度耗时 | 9,214.960 ms | 7,866.637 ms |
| 任务计数聚合命令 | 4,001 | 0 |
| find 命令 | 504 | 505 |
| 成功分配数 | 500 | 500 |
| 单节点最大占用 | 63 | 63 |

MongoDB 将 `count_documents` 转换为 aggregate 命令。新实现用一次投影查询替代 4,001 次计数，但仍保留必要的逐任务原子领取、运行记录、运行锁写入及节点准入读取。原始报告在本机 `.local/scheduler-before-majority.json` 和 `.local/scheduler-after-majority.json`；计数已排除种子写入及结果断言查询。优化前函数取自提交 `562f621` 的源码，由相同基准脚本调用；较早的默认写入确认测量保留在其他本地报告中，不与本表混用。

以上是历史单次本机元数据基线，时间受 MongoDB 写入延迟影响，也不证明五百路协议采集或二十四小时容量。报告 `passed` 不表示全部设计验收通过。事务取消和接管的验证方法见 `docs/scheduler-transactions.md`。
